# ADR-002: OCR held constant: Tesseract 5 with tessdata_best Arabic and English

Status: accepted, 20 November 2026

## Context

The benchmark compares models, so every model must read exactly the same text. That means one
OCR step, run once, with its output committed. It also has to be measured on its own, so every
wrong field can be traced to OCR (the value never reached the model) or to the model (it did,
and the model got it wrong). The budget rules out paid OCR APIs, and documents must not leave
the machine.

## Decision

- **Engine:** Tesseract 5.3.4, the version Ubuntu 24.04 ships, in a Docker image built from
  `ubuntu:24.04` pinned by digest (`ocr/Dockerfile`). No system install is needed.
- **Models:** `tessdata_best` Arabic and English at commit `e12c65a9`, downloaded by the
  Dockerfile and checked by sha256. Tesseract's own documentation ranks `tessdata_best` as the
  most accurate set; the Ubuntu language packages track the faster, less accurate set.
- **Settings:** `-l ara+eng --oem 1 --dpi 300 -c preserve_interword_spaces=1`, PDFs rasterised
  at 300 dpi in greyscale with pypdfium2.
- **Page segmentation mode 4**, chosen by a pilot rather than by taste. `python -m ocr pilot` ran
  modes 3, 4 and 6 over the 60 base documents and measured how many true field values survive
  into the OCR text. That measure was chosen because it is what limits extraction:

  | Mode | Field values present in OCR text | Character error rate (normalised, line-aligned) | Same, strict reading order |
  |---|---|---|---|
  | 3 | 79.1% | 19.9% | 34.7% |
  | **4** | **79.3%** | **9.8%** | **9.7%** |
  | 6 | 77.2% | 11.6% | 11.2% |

  The full result is in `data/ocr/_pilot.json`. The pilot ran on the same 60 documents that are
  scored, so the choice is tuned on the test set. Modes 3 and 4 are within a percentage point on
  field values, so the rule treats them as tied and the error rate decides (9.8% against 19.9%);
  character error rate alone picks the same mode. The figures are from the final code, after
  the fixes to the grounding check and to the error rate's line alignment described below.

## What OCR does to the documents

Measured on the 60 base documents with mode 4 (`data/ocr/_scores.json`):

| Layout | Character error rate | True field values present in the OCR text |
|---|---|---|
| English | 0.08% | 100% |
| Bilingual | 15.8% | 86.1% |
| Arabic | 13.6% | 53.8% |
| Scanned-look (15, 200 dpi) | 19.2% | 75.2% |

**Tesseract cannot read Arabic-Indic digits.** On pages printed with ٠١٢٣٤٥٦٧٨٩, 64 of 71
amounts, dates, TRNs and document numbers never reach the model. The Arabic model returns
Latin lookalikes instead: ٧٨٨٣ comes out as `VAAY`. Running Arabic alone, without English, gives
the same result, so this is the model and not the language mix. The Arabic language data has
not changed since 2017.

Arabic pages printed in Western digits lose fewer, 13 of 35, and bilingual pages in Western
digits only 2 of 71. The losses on Arabic pages come from layout, not from reading digits: the `د.إ` marker is
often read as `1.5` and glued to the amount beside it (`295.471.5`), and table cells run
together (`415.7514,967.00`). Arabic names and labels survive well: 6 of 50 text values lost on
Arabic pages, 3 of 60 on bilingual ones.

**OCR also filters injections.** Of the 10 poisoned documents, 8 instructions survive OCR; the 2
in white text never reach the model. (A first version printed the fine-print injections in a grey
light enough that OCR dropped them too, which left only 5 documents to test injection resistance
on; they were darkened to a grey OCR still reads.) The white text is reported as a property of the
pipeline, not as a defence. The oracle text source sends all 10 to the model.

## Consequences

- On Arabic pages about half of the true values are missing before any model runs, so no model
  can reach the scope's Arabic target through this OCR. That is the main finding the scope's risk
  table anticipated, and it is reported as such.
- Every model is also run on the `oracle` text source (the generator's exact text, including
  hidden text) to show what each model does when OCR is taken out of the picture. The scope
  suggested the PDF text layer for this upper bound; pdfium's text layer reverses some Arabic
  words and splits right-to-left rows, so it is not a clean upper bound, and the generator's
  text is used instead.
- The error rate aligns lines regardless of order, and joins back a line OCR split or merged
  before scoring it, so a wrapped line is not counted as a lost one. The strict in-order rate is
  published beside it, and the two agree within a point on clean pages.
- The grounding check (`bench/grounding.py`) was corrected while measuring this: it used to join
  digit runs separated by spaces, which glued an amount to the misread currency marker beside
  it, and it needed a space between a written month and the year, which OCR often drops. Both
  made correct values look absent. Both are pinned by tests that fail on the old code.

## Alternatives for v2

- An OCR engine that reads Arabic-Indic digits. Candidates to test: TII's Falcon-OCR (270M
  parameters, Apache-2.0; its Arabic coverage is not stated), PaddleOCR's Arabic model,
  Surya and Qari-OCR. Changing OCR means a new results table, not an edit to this one.
- A digit-repair pass that maps Latin lookalikes back to Arabic-Indic digits would raise the
  numbers, but it would be fitted to this dataset's font. It is not in v1.
